1. Objective
Milestone 3 proved that people can use your app. Milestone 4 proves that it keeps working when you change it: every P0 story is checked by automated tests that a machine can run in seconds, after every change.

A test that cannot fail is not a test. Before you commit a test, break the rule on purpose — change <= to <, or 3 hours to 4 — and run the tests. If nothing turns red, the test is not checking what you think. Put the code back, then commit.

2. What to write
One new document: docs/testing.md in your team repository. Markdown only. The tests themselves go in tests/.

docs/SETUP.md must still work — add how to run the tests.

Four sections, in this order. Numbers in bold are minimums.

Section	Minimum	What it must contain
1. What we test, and why	1 table	For each layer (services, repository, routes, interface): what kind of test it gets, or why it gets none. Then two or three sentences on risk: which parts you tested most, and why those.
2. Test cases for every P0 story	every P0 story
3 test cases each	A table: ID · Story · Input · Expected result · Kind. Every P0 story has at least three test cases: at least one normal case that succeeds, at least one error case where a business rule refuses the input, and — if the rule has a number in it (a limit, a time, an amount) — boundary cases on both sides of that number.
3. Automated tests	every test case in section 2	Every test case in section 2 is a pytest test in tests/, with its ID in the test name or a comment. One command runs them all. Tests run without a server and without your real database (use a fake repository or a temporary database). Show the command and a screenshot of the output.
4. What the tests found	1 entry	A bug your tests found: the issue, the fix, and the test that now guards it. If your tests found none, show one rule you broke on purpose and the red test output it produced.
The rule that decides most of your mark

At the Sprint 4 Review session, the instructor clones your repository onto a machine that has never seen your project and runs these checks:

Check	What the instructor does	Pass when
1. Setup	Clone and follow docs/SETUP.md	the app runs with no errors
2. Tests run	Type pytest on that machine	all tests pass, with no hand edits
3. Every P0 story	Pick a P0 story in docs/testing.md	it has 3 or more test cases, including an error case
4. Boundary	Read one test for a rule with a number limit	it checks both sides of the limit
5. Traceable	Pick one test case ID in the table	its pytest test exists and passes
Test this yourselves before the deadline: clone into a new folder and run pytest. Tests that only pass on one laptop usually read a file that was never committed, or depend on today's date.

3.3 Automated tests
tests/test_booking.py — one test per test case, the ID in the name or comment:

import pytest
from datetime import datetime, timedelta
from src.booking import duration_ok, create_booking, BookingError
from tests.fakes import FakeBookingRepo
START = datetime(2026, 12, 7, 18, 0)

@pytest.mark.parametrize("minutes, ok", [
    (179, True),    # TC-04  2:59
    (180, True),    # TC-05  3:00 is allowed
    (181, False),   # TC-06  3:01
])
def test_booking_length(minutes, ok):
    assert duration_ok(START, START + timedelta(minutes=minutes)) == ok

def test_tc07_second_active_booking_is_refused():
    repo = FakeBookingRepo(active={"s01": 7})
    with pytest.raises(BookingError) as err:
        create_booking(repo, "s01", "A12", START, START + timedelta(hours=2))
    assert err.value.status == 409
    assert repo.saved == []
Run them all: python -m pytest -v — 18 passed in 0.27 s (screenshot below).

3.4 What the tests found
Bug #71 — a 27-hour booking was accepted. duration_ok used (end - start).seconds, which ignores whole days, so 1 day and 3 hours looked like 3 hours. Found by test_booking_longer_than_a_day. Fixed in PR #72 with total_seconds(); the test stays as a regression test.

5. Submission workflow
One member creates a branch, e.g. docs/m4-testing
Commit docs/testing.md on that branch
Open a Pull Request into main
Another member reviews and approves, leaving at least one substantive comment
Merge the Pull Request into main
Export the merged testing.md to PDF and submit on the LMS
Use the Review changes button, not the comment box at the bottom of the page — a plain comment is not recorded as a review.

The tests themselves arrive through their own pull requests during the sprint.
