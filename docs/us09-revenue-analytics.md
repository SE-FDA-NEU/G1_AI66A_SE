# US09 - Seller Revenue Analytics

**Issue:** #21
**Priority:** P1 - Should have
**Story Points:** 5
**Related route:** `/seller/analytics`

---

## 1. User Story

As a seller, I want to view revenue statistics generated from my completed orders, so that I can understand the performance of my store over a selected period.

---

## 2. Feature Overview

The Seller Revenue Analytics page provides a seller with a summarized view of store performance based only on completed sales belonging to that seller.

The page must allow the seller to:

* view total revenue;
* view supporting sales statistics;
* inspect revenue performance over time;
* filter analytics by date range;
* clearly understand when there is no revenue data;
* retry when analytics cannot be loaded.

All analytics must be calculated only from the authenticated seller's own completed order items.

---

## 3. Analytics Dashboard Layout

The `/seller/analytics` page is organized into three main areas.

### 3.1 Header and Date Filter

The top section contains:

* page title: `Revenue Analytics`;
* currently selected date range;
* date-range selector;
* refresh/apply action when required.

The default date range is:

`All time`

The seller may select:

* All time;
* Last 7 days;
* Last 30 days;
* Custom date range.

For a custom range, the seller selects:

* `From`;
* `To`.

The selected range applies to every metric and visualization on the page.

---

### 3.2 Revenue Summary

The dashboard displays the following summary statistics.

#### Total Revenue

The total revenue earned by the seller from eligible completed order items within the selected period.

#### Completed Orders

The number of distinct completed orders containing at least one item belonging to the seller.

A multi-seller order is counted once for a seller if that order contains at least one item belonging to that seller.

#### Items Sold

The total quantity of the seller's items contained in eligible completed orders.

Conceptually:

`Items Sold = Σ quantity`

#### Average Revenue per Completed Order

The average seller revenue generated by completed orders within the selected period.

Conceptually:

`Average Revenue = Total Revenue / Completed Orders`

If there are no completed orders:

`Average Revenue = 0`

These metrics provide additional context so that the seller does not have to evaluate store performance from the total revenue value alone.

---

### 3.3 Revenue Trend

The dashboard displays revenue over time for the selected period.

Each data point represents revenue generated from completed order items belonging to the authenticated seller.

The trend uses:

* daily aggregation for ranges up to 31 days;
* weekly aggregation for ranges longer than 31 days and up to 180 days;
* monthly aggregation for longer ranges and `All time`.

The revenue trend must use the same revenue calculation and seller-isolation rules as the summary metrics.

Changing the date range refreshes both the summary statistics and the revenue trend.

---

## 4. Eligible Orders

Revenue analytics include only orders whose business status represents successful completion.

The canonical eligible status for US09 is:

`COMPLETED`

Orders in states such as:

* pending;
* processing;
* cancelled;
* rejected;
* refunded;

must not contribute to revenue analytics.

US08 and other order-management features should use a compatible order-status model so that `COMPLETED` has an unambiguous meaning throughout the system.

---

## 5. Revenue Calculation Rule

Revenue must be calculated from the authenticated seller's own order items rather than from the total value of the entire order.

For seller `s`:

`Revenue(s) = Σ(unitPriceAtPurchase × quantity)`

for all order items satisfying:

* the item belongs to seller `s`;
* the parent order has status `COMPLETED`;
* the order completion timestamp belongs to the selected date range.

### Example

A completed order contains:

**Seller A**

* Mouse: `2 × 20 = 40`

**Seller B**

* Keyboard: `1 × 50 = 50`

Total order value:

`90`

Revenue shown to Seller A must be:

`40`

and not:

`90`

The same isolation rule applies to all supporting analytics metrics.

For Seller A:

* Items Sold increases by `2`;
* the order contributes once to Completed Orders;
* only `40` contributes to Total Revenue.

---

## 6. Historical Price

Revenue must use the price recorded when the customer placed the order.

Conceptually:

`orderItem.unitPriceAtPurchase`

must be used rather than:

`product.currentPrice`

Changing the current price of a product must not modify historical revenue analytics.

This guarantees that previously completed sales remain historically consistent.

---

## 7. Seller Data Isolation

### BR7 - Seller Revenue Isolation and Calculation

Analytics must include only order items belonging to the authenticated seller.

For every analytics request:

`sellerId = authenticatedUser.id`

The seller ID used for analytics must come from the authenticated session or authorization context.

The analytics page must not accept an arbitrary seller ID supplied by the client as the source of authorization.

A seller must never receive:

* another seller's revenue;
* another seller's sold quantities;
* another seller's completed-order statistics;
* another seller's revenue trend data.

---

## 8. Date Range Filtering

Revenue analytics may be filtered by completion date.

The relevant timestamp is:

`completedAt`

rather than:

`createdAt`

This means an order contributes to analytics based on when it becomes completed, not when it was initially created.

For a selected range:

`from <= completedAt <= to`

All displayed analytics must use the same selected range, including:

* Total Revenue;
* Completed Orders;
* Items Sold;
* Average Revenue per Completed Order;
* Revenue Trend.

### All-time behaviour

If `All time` is selected, every eligible completed order available to the authenticated seller is included.

### Custom range validation

For a custom date range:

* both start and end dates must be valid;
* the start date must not be later than the end date;
* an invalid range must display a validation message;
* analytics must not refresh using an invalid range.

Suggested validation message:

`Start date must be earlier than or equal to end date.`

The exact API timestamp and timezone representation will be defined during the API/architecture milestone.

## 10. UI States

The analytics feature must explicitly support the following states.

### 10.1 Loading State

While analytics are being retrieved:

* the page remains visible;
* analytics content displays a loading indicator or skeleton state;
* stale data must not be presented as newly refreshed data.

Suggested text:

`Loading analytics...`

---

### 10.2 Success State

When analytics are loaded successfully:

* summary statistics are displayed;
* revenue values are formatted consistently using the marketplace currency;
* the selected date range is visible;
* revenue trend data corresponds to the same selected range.

---

### 10.3 Empty State

If no completed seller orders exist in the selected period:

* Total Revenue = `0`;
* Completed Orders = `0`;
* Items Sold = `0`;
* Average Revenue per Completed Order = `0`;
* no fabricated revenue trend data is displayed.

Suggested message:

`No completed sales found for this period.`

The page remains valid.

An empty result is not an application error.

---

### 10.4 Error State

If analytics cannot be loaded because of a system, network, or server error:

* the application must distinguish this from an empty result;
* revenue must not silently appear as zero;
* an understandable error message is displayed;
* the seller is given an option to retry.

Suggested message:

`Unable to load revenue analytics. Please try again.`

Suggested action:

`Retry`

---

## 11. Revenue Presentation

Revenue values must be presented consistently throughout the dashboard.

The interface must:

* use the marketplace's configured currency;
* use consistent decimal formatting;
* clearly distinguish revenue values from counts such as orders or items;
* label every summary metric;
* show the active date range so that sellers understand the period represented by the numbers.

For example:

```text
Revenue Analytics
Last 30 days

Total Revenue          12,500,000
Completed Orders              42
Items Sold                    67
Avg. Revenue / Order     297,619

Revenue over time
[trend visualization]
```

The exact visual styling is deferred to the UI design milestone.

---

## 12. Multi-Seller Order Behaviour

An order may contain products belonging to multiple sellers.

Analytics must therefore operate at the order-item level.

The full order value must never automatically be attributed to every seller participating in the order.

For each seller:

* revenue includes only their own items;
* items sold includes only their own quantities;
* the completed order may count once toward their Completed Orders metric if it contains at least one of their items.

### Example

Order #100 contains:

```text
Seller A:
2 × Product X

Seller B:
1 × Product Y
```

For Seller A:

* only Product X contributes to revenue;
* Items Sold increases by `2`;
* Completed Orders increases by `1`.

For Seller B:

* only Product Y contributes to revenue;
* Items Sold increases by `1`;
* Completed Orders increases by `1`.

Neither seller receives the complete order value as their revenue.

## 14. Acceptance Criteria

### AC1 - View revenue analytics

**Given** I am an authenticated seller and completed orders containing my products exist,
**when** I open `/seller/analytics`,
**then** I see revenue analytics calculated only from my completed seller order items.

---

### AC2 - View summary statistics

**Given** eligible completed sales exist,
**when** analytics finish loading,
**then** I see:

* Total Revenue;
* Completed Orders;
* Items Sold;
* Average Revenue per Completed Order.

All metrics must represent the same selected date range.

---

### AC3 - View revenue performance over time

**Given** completed sales exist within the selected range,
**when** analytics are displayed,
**then** I can see how my revenue is distributed over that period using the revenue trend.

---

### AC4 - Filter analytics by date

**Given** I select a valid date range,
**when** the analytics are refreshed,
**then** only orders whose `completedAt` timestamp belongs to that period contribute to the displayed analytics.

---

### AC5 - Invalid date range

**Given** I select a custom start date later than the end date,
**when** I attempt to apply the range,
**then** I see a validation message and analytics are not refreshed using the invalid range.

---

### AC6 - Empty period

**Given** I have no completed sales in the selected period,
**when** analytics are displayed,
**then** all summary metrics show zero and I see a clear empty-state message.

---

### AC7 - Seller isolation

**Given** I am authenticated as Seller A,
**when** revenue analytics are calculated,
**then** products and revenue belonging to Seller B or any other seller are never included in my analytics.

---

### AC8 - Loading state

**Given** analytics data is still being retrieved,
**when** I open or refresh the analytics page,
**then** I see a loading state until the request completes.

---

### AC9 - Error state

**Given** analytics data cannot be retrieved,
**when** the request fails,
**then** I see an error message and a retry option rather than an incorrect zero-revenue result.

---

### AC10 - Historical consistency

**Given** a completed order exists and a product's current price is later changed,
**when** I view revenue analytics,
**then** historical revenue continues to use the price recorded on the original order item.

---

## 15. Business Rule Summary

| Rule               | Requirement                                        |
| ------------------ | -------------------------------------------------- |
| Eligible order     | Only `COMPLETED` orders contribute                 |
| Revenue basis      | `unitPriceAtPurchase × quantity`                   |
| Seller isolation   | Only authenticated seller's order items            |
| Time basis         | `completedAt`                                      |
| Historical pricing | Current product price must not change past revenue |
| Multi-seller order | Calculate each seller independently at item level  |
| Empty result       | Valid result with zero metrics                     |
| Request failure    | Error state, not zero revenue                      |
| Filter consistency | Every metric uses the same selected range          |

## 17. Out of Scope for US09

To keep US09 within its current story scope, the following features are not required:

* profit or cost calculation;
* tax analytics;
* refund analytics;
* revenue forecasting;
* customer segmentation;
* exporting analytics reports;
* comparison against other sellers;
* marketplace-wide analytics;
* advanced product-ranking analytics.

These features may be introduced through separate stories if required later.
